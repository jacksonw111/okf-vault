# 多模态大模型驱动的 UI 自动化测试

把"**自然语言用例描述 + 页面截图 + DOM 树**"同时喂给多模态大模型，让模型自己规划步骤、定位元素、生成代码、执行失败再自调——把 UI 测试从"人工写脚本"推到"**描述即生成**"。

## 适用场景

- 业务界面迭代快、UI 元素多，元素 ID 不稳定或没有稳定 ID；
- 测试用例数量大、人工维护成本高（千万级 → 7000+ 自动生成）；
- 现有规则/录制类自动化工具对动态内容、复杂交互乏力；
- 团队希望测试人员**只写"做什么"**而不是"怎么点"。

## 四阶段演进（最关键的认知）

| 阶段 | 关键做法 | 致命短板 |
|------|---------|---------|
| 1. 文本属性驱动 | 提取按钮/标签文本，让模型按文本匹配 | 动态内容易失效；图标/图片按钮无文本 |
| 2. 唯一 ID 驱动 | 埋点平台为每个控件分配稳定 ID | 前期 ID 维护成本高，可扩展性差 |
| 3. **多模态融合** | 截图 + DOM + 文本描述一起进模型 | 仍需人写"详细步骤"用例描述 |
| 4. **自主推理 + 动态调试** | 高层描述 + 截图 → 端到端生成 + 执行失败自动重写 | 算力/Token 成本高，需容错上限 |

**核心结论**：**不要在元素标识的稳定性上死磕**（阶段 2 的教训），**让模型直接看图**才是正路（阶段 3 起的方向）；阶段 4 把"测试人员要写多详细"也一并消解掉。

## 系统架构（五层）

1. **用户交互层**：URL + 自然语言用例描述输入；展示生成结果 + 人工审核编辑。
2. **API 层**：调试代码生成服务 + AI 运行服务（与多模态大模型通信、与执行设备实时连接）。
3. **AI 核心层**（智能大脑）：
   - 多模态推理：截图 + DOM + 描述 → 操作步骤序列；
   - 动态代码生成：模板化 + 参数化，按当前页面状态实时生成 Python 代码；
   - 强化学习式反馈：执行失败 → 收集错误 → 调整策略 / 重写定位 / 重规划步骤。
4. **执行引擎层**：
   - DOM 结构化分析 + 视觉坐标索引 + 坐标校准（多模态元素定位）；
   - 自适应执行：连续失败检测、页面状态变化监测、智能重试；
   - 实时把执行状态、错误、页面变化回传给 AI 核心层。
5. **基础设施层**：复用公司基础框架。

## 端到端生成流程

```
文本用例管理平台
   ↓（目标页面 + 自然语言描述）
调试代码生成服务 → 预执行代码
   ↓
UI 脚本运行平台（设备启动、进入页面）
   ↓
AI 生成服务：实时多模态采集
   - 页面截图（含控件标注）
   - 简化 DOM 树
   - 用户用例描述
   ↓
规划步骤序列 → 每步：多模态定位 → 生成 Python 代码片段
   ↓
真实设备执行 → 成功？
   ├─ 是 → 完成？合并输出完整脚本
   └─ 否 → 容错（重写代码 / 重规划步骤）→ 超过阈值则告警
   ↓
完整代码 → 人工审核 → UI 自动化用例仓库
```

## 关键设计点

- **多模态元素定位**：把 DOM 树 + 截图视觉坐标建索引、坐标校准——不要只靠 DOM 也不要只靠视觉。
- **生成 + 执行紧耦合**：每生成一段代码就立刻在真实设备执行，不要攒着最后跑——这样才能拿到"刚生成的代码在新页面里能不能跑"的真实反馈。
- **容错要设硬上限**：连续失败超过阈值必须告警 + 抛出异常，避免无限循环烧 Token。
- **强化学习式反馈回路**：执行失败的原因（元素未找到 / 断言失败 / 页面变化）回灌给模型，让下一步规划有依据。
- **人工审核不可省**：AI 生成的代码进入仓库前过一遍人审，挡住业务逻辑错误。

## 实践效果（数据参考）

- 累计自动生成 UI 测试用例 **7000+**；
- 整体生成成功率 **80%+**；
- UI 自动化用例覆盖率 **~80%**；
- 半年内通过生成用例发现前端缺陷 **300+**（交互逻辑、数据显示等）。

## 验证 / 自检

- [ ] 是否能用一句话说清"输入是什么、模型做什么、输出是什么"？
- [ ] 元素定位是否真的用了多模态（不只是 DOM 或不只是视觉）？
- [ ] 执行失败是否有回灌模型的反馈回路？
- [ ] 容错是否设了硬上限（避免无限循环）？
- [ ] 是否有"测试人员只写高层描述"的明确边界，而不是仍要求详细步骤？
